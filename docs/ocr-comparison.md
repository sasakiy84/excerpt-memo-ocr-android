# OCR と湾曲補正の比較

2026-11-02 / 方解抄 0.5.0

## 採用方式

NDLOCR-Lite のレイアウト検出を最初に一度実行し、文字認識を始める前に処理を決める。

| ページの特徴 | 処理 |
|---|---|
| 長い縦書きの行が大半 | PP-OCRv6 small の検出と認識 |
| 長い横書きの行が多く、行ボックスが行間隔に比べて厚い | UVDoc → NDLOCR の行検出 → PP-OCRv6 small の認識 |
| その他。今回の新聞を含む | NDLOCR-Lite の検出と認識 |

モデル選択の UI は設けない。モデルを並列実行したり、複数の OCR 結果を生成して競わせたりしない。UVDoc は必要と判定したページに一度だけ使い、再読取りでは補正済み画像をそのまま認識する。処理は既存の単一ワーカー上で直列に実行する。

UVDoc の結果を画面と保存画像にも使い、文字の選択座標を一致させる。元画像は別に保持し、手動の切り抜き・回転をやり直せる。PP-OCR の結果には NDLOCR のページ番号・ルビ・表の区分を対応付け、PP 検出で落ちた小さなページ番号は補う。

判定は `OcrRouting.java` に集約した。本文行の 70% 以上が縦書きで、3 行以上あり、行高の中央値が画像高の 35% を超える場合を長い縦書きとする。横書き補正の条件は、横書きが 60% 以上、画像幅の 30% 以上の行が 8 本以上、隣接する行との中心間隔に対する行高の比の中央値が 1.2 を超える場合。閾値は今回の資料で決めたもので、未知の資料への精度保証ではない。

## 画像と評価方法

提供された画像から同一 SHA-256 の重複を除き、3 枚の 900 × 1200 px を主評価に使った。同じ本の 600 × 800 px 版は縮小時の補助評価とし、集計に二重計上していない。

| ID | 内容 | SHA-256 |
|---|---|---|
| A | 縦書きの書籍、32 ページ、傾きと湾曲 | `f6a514327fce745d72f99ce49c4730d9dc0651147e96415455bb76507a48f940` |
| B | 新聞、細かな縦組みの複数段、影 | `8dd6a64a0265b50786b579da719b7731cb040124d9a5058ed5ff8d9cf472d8dd` |
| C | 横書きの問題集、湾曲、傾き、赤い下線 | `dc454b2c84ad8e684ae6fe217ac9a1d9784aa656943e2b44365908f71fe5c5c5` |
| A 縮小 | A と同じ内容 | `cc8c1652eef1f5725ba94c2a47e463532c0005a14af764ca817987a44fd845dc` |

A から 4 箇所・279 字、B から 3 箇所・194 字、C から 3 箇所・174 字、合計 10 箇所・647 字を目視で転記して評価した。指標は **抜粋 CER**。正解の各抜粋に対し、認識結果中の連続した部分文字列との最小編集距離を求め、挿入・削除・置換の合計を正解文字数で割った。抜粋の外側の前後だけは誤りに数えず、抜粋内部の欠落や混入は数える。NFKC と空白除去は評価時だけ適用し、アプリのコピー内容には適用しない。

全文 CER、検出再現率、ページ全体の読み順の正しさを表す指標ではない。今回の写真を使って方式と閾値を選んでおり、独立した検証データはない。写真、転記、全文の認識結果は Git や公開リリースへ追加していない。

## アプリの Java コードでの再測定

採用前に、実際の `OcrEngine.read` と `readPage` を Robolectric API 36 / native graphics で実行した。推論にはアプリと同じ ONNX Runtime **1.24.3** の Linux CPU 版を使用し、OpenCV のホスト版は **4.9.0**。認識結果をモックしていない。各画像・方式でエンジンを作り直し、初回 1 回の後に 3 回測定した。下表はその中央値。補正画像の出力も確認した。

| 画像 | 現行の秒 | 採用方式の秒 | 時間比 | 現行の抜粋 CER | 採用方式の抜粋 CER |
|---|---:|---:|---:|---:|---:|
| A 書籍 | 2.180 | 2.125 | 0.97 倍 | 21/279 = 7.53% | 2/279 = 0.72% |
| B 新聞 | 3.715 | 3.365 | 0.91 倍 | 2/194 = 1.03% | 2/194 = 1.03% |
| C 問題集 | 4.405 | 3.730 | 0.85 倍 | 56/174 = 32.18% | 4/174 = 2.30% |
| A 縮小（補助） | 1.678 | 2.035 | 1.21 倍 | 12/279 = 4.30% | 2/279 = 0.72% |

主評価 3 枚では **79/647 = 12.21% → 8/647 = 1.24%**。各画像の時間が現行の 2 倍未満であることと、主評価の合計誤り数が減ることを任意の実画像テストでも検査した。Python 比較実装とは補間処理・実行ランタイムが異なり、数文字の違いがある。採用判断にはこちらの Java 実装の結果を優先する。

この測定も Linux ホスト CPU 上の結果であり、物理 Android 端末の性能値ではない。測定中は Android ソフトウェアエミュレーターのバックグラウンド処理もあり、秒数の小さな差には意味を持たせない。

### Android 側の確認範囲

Android 16 のローカルエミュレーターで、PP-OCR の日本語・英語認識と、ドロワー・文字選択・コピー・画面再作成の操作テストが成功した。UVDoc の CPU 推論は、ハードウェア仮想化のないエミュレーターでは 20 分で時間切れとなり、Android 上での完走は確認できていない。ホストの Java 実装では同じモデルによる補正と、その後の認識を確認したが、この結果を Android の成功とは扱わない。

UVDoc の XNNPACK 実行も試したが、セッション生成時にプロセスが異常終了したため採用しなかった。配布版では従来と同じ CPU Execution Provider を使う。物理端末での UVDoc の完走、速度、メモリ、消費電力は未確認であり、上表の時間比がそのまま端末に当てはまるとは限らない。

## Python 比較実装の測定

Linux x86_64、AMD EPYC 9V74、割当 CPU 5 コア、Python 3.12.14、ONNX Runtime 1.31.1、OpenCV 5.0.0、NumPy 2.5.4。CPU Execution Provider を使用。検出は最大 4 スレッド、認識と UVDoc は 2 スレッド、OpenCV は 1 スレッド。GPU・NNAPI は使っていない。

各方式・画像で初回 1 回と、その後 3 回を実行。下表の時間はモデル読込後 3 回の中央値で、ページ全体の前処理・検出・文字認識・読み順整序を含む。Android 実機の待ち時間や消費電力を測った値ではない。

各セルは「秒 / 抜粋 CER」。

| 方式 | A 書籍 | B 新聞 | C 問題集 |
|---|---:|---:|---:|
| NDLOCR-Lite（現行） | 1.715 / 7.53% | 3.237 / 1.03% | 4.278 / 35.63% |
| PP-OCRv6 small | 1.039 / 1.08% | 1.632 / 72.16% | 1.948 / 55.17% |
| NDLOCR 検出 + PP 認識 | 1.372 / 13.62% | 2.247 / 4.64% | 1.932 / 48.85% |
| UVDoc + NDLOCR | 2.158 / 23.30% | 2.993 / 9.28% | 2.771 / 4.60% |
| UVDoc + PP-OCR | 1.301 / 1.43% | 1.861 / 72.16% | 2.198 / 2.30% |
| UVDoc + NDLOCR 検出 + PP 認識 | 1.340 / 35.13% | 2.448 / 13.40% | 2.362 / 2.87% |
| **採用する自動判定** | **1.849 / 0.72%** | **3.179 / 1.03%** | **3.059 / 2.87%** |

採用方式は 3 枚合計で **9 / 647 字、1.39%**。現行は **85 / 647 字、13.14%**。時間は現行の **1.08 / 0.98 / 0.72 倍**だった。A の縮小版では現行 1.530 秒・3.94%、採用方式 1.510 秒・0.72%。

比較用 PP の DB 後処理は公式同様の polygon unclip。採用方式では Android に合わせて、最小外接矩形の辺を unclip 距離だけ平行移動する。検出端のわずかな差で、A の PP 単体と採用方式の CER は一致しない。

初回の時間には、その時点で未読込のモデルの初期化も入る。同一プロセスで A → B → C → A 縮小の順に測定しているため、B 以降は完全なコールドスタートではない。

| 方式 | A の初回 | B の初回 | C の初回 | プロセス最大 RSS |
|---|---:|---:|---:|---:|
| NDLOCR-Lite | 7.964 秒 | 3.035 秒 | 4.326 秒 | 821 MiB |
| 採用する自動判定 | 2.878 秒 | 7.172 秒 | 3.068 秒 | 1183 MiB |

RSS は Python プロセスで複数画像を連続処理したときの最大値であり、モデルファイル量や Android アプリの必要メモリ量とは異なる。実機でのメモリ・処理時間・消費電力は未測定。

## 判断の理由

PP-OCR の検出は A の長い縦組みでは有効だった。一方 B の新聞では隣接列を横長の領域としてまとめてしまい、文字列が混ざる。全ページを PP へ切り替える方式は採用しない。

UVDoc は C の湾曲と傾きを緩和し、現行で多数あった文字の欠落・混入を減らした。A や B に常時適用すると、行の検出・切り出しが崩れて悪化する組み合わせもある。全画像への補正は採用しない。

回転だけで済ませる補助実験も行った。C の中央領域（横 12〜78%、縦 10〜70%）を適応二値化し、行投影の分散が最大になる角度を −12〜12°・0.5°刻みで探索すると −3.5°になった。その前後 1°を含む 3 角度で NDLOCR・PP-OCR・NDLOCR 検出 + PP 認識を試したが、最良でも 37/174 字、21.26% の抜粋 CER だった。今回の湾曲したページでは回転補正だけでは足りず、UVDoc を使う構成を採用した。この補助実験は Python 実装での確認で、上の Java 実装の測定とは別に扱う。

UVDoc の形状推定ネットワークの内部入力（高さ 712 × 幅 488）を小さくする方法も補助実験した。356 × 244 では C が 113/174 字、256 × 176 では 131/174 字の誤りとなり、元の解像度を維持した。これらの変更モデルは配布せず、アプリには公式 ONNX をそのまま同梱する。

認識の信頼度を見て別モデルで再試行する方式も比較したが、C の時間が約 7.64 秒まで増えた。採用方式は最初のレイアウトから一つの経路を選び、不要な認識のやり直しを避ける。

## モデル量と実装

| モデル | バイト数 |
|---|---:|
| NDLOCR-Lite 既存 4 モデル | 157,110,896 |
| PP-OCRv6 small 検出 | 9,880,512 |
| PP-OCRv6 small 認識 | 21,159,378 |
| UVDoc | 31,684,150 |
| **同梱モデル合計** | **219,834,936（現行の 1.40 倍）** |

モデルファイル量は許容上限の 2 倍以内。モデルは必要になった時点で読み込み、ページ間で再利用する。PP 文字表は公式配布設定から抽出し、CTC の blank と末尾の空白を実行時に加える。再学習・量子化・モデル構造の変更はしていない。

PP 検出は BGR、ImageNet mean/std、最大辺 1024。DB の二値化 0.2、領域平均 0.45、unclip 比 1.4。四辺形を透視変換で切り出す。認識は縦長の行を反時計回りに回転し、高さ 48・幅 320〜3200 にアスペクト比を保って整形、BGR を −1〜1 に正規化して greedy CTC 復号する。

UVDoc は BGR の 0〜1、NCHW を入力する。公式 ONNX に内部の resize、変形グリッド、GridSample が含まれるので、外側でグリッド補正を重ねない。出力は同じ大きさの BGR 画像。既存 NDLOCR 認識の BGR 入力は上流 PARSeq の前処理に合わせて維持した。

## 再実行

提供写真と転記をローカルの外部ディレクトリへ置く。転記 JSON は `{ "user-01.jpg": ["抜粋1", "抜粋2"] }` の形式。

```sh
python3 -m venv /tmp/ocr-evaluation-venv
/tmp/ocr-evaluation-venv/bin/pip install -r scripts/requirements-ocr-benchmark.txt
/tmp/ocr-evaluation-venv/bin/python scripts/benchmark-ocr.py \
  --workflow auto --truth /path/to/truth.private.json \
  --output /tmp/ocr-results/auto.json \
  /path/to/user-01.jpg /path/to/user-02.jpg /path/to/user-03.jpg
```

`--workflow` に `ndl`、`pp`、`hybrid`、`uv-ndl`、`uv-pp`、`uv-hybrid` を指定すると各方式を比較できる。標準ではリポジトリ内の固定済みモデルを使用する。

Android に組み込んだ Java コード自体の比較は、同じ写真と `truth.private.json` を持つディレクトリを指定する。

```sh
OCR_EVALUATION_DIR=/path/to/evaluation \
  python3 scripts/gradle-cloud.py --no-daemon testDebugUnitTest \
  --tests '*PrivateOcrBenchmarkTest' --rerun-tasks
```

写真は `input/user-01.jpg`、`input/user-02.jpg`、`input/user-03.jpg`、`input/user-05.jpg` に置き、`results/` を作成しておく。この任意テストは指定がなければスキップする。ベンチマーク用の全文結果は外部ディレクトリに保存する。
